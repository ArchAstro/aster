Decision spec · proposed

Aster-owned dynamic service ports

Allocate one collision-free port bundle per aster services up run, hold OS-backed leases for the supervisor lifetime, and inject the resolved values into every service without generating worktree-specific env files.

DSLExtend named ports with allocation = "dynamic"; preserve every existing static form.
CoordinationSerialize allocation with a host-level lock and hold per-port lease locks until shutdown.
PropagationAdd typed port_env for numeric values; retain templates for composed strings and URLs.

1. Decision options

OPTION 1 · RECOMMENDED

Extend the existing named-port model

Dynamic ports become a new resolution mode. Services continue referencing stable global port names, so current control ports, TLS routes, offsets, cleanup, and templates remain one model.

Tradeoff: port ownership remains conventional rather than nested under a service. Cost: medium, approximately 2–4 engineering days plus FirstLanding smoke coverage.

OPTION 2

Move ports under services

Declare [dev.services.platform.ports.http] and reference {services.platform.ports.http}. Ownership is explicit, but control/TLS ports need a second model and FirstLanding requires a broad rewrite.

Tradeoff: conceptually pure but duplicates today’s named-port graph. Cost: high, approximately 5–8 days.

OPTION 3

Add first-class allocation slots

Allocate a worktree slot and derive every port from a configured base plus offsets. This mirrors FirstLanding’s historical port bands.

Tradeoff: compact for one monorepo, but one overlooked listener recreates the current collision class. Cost: medium, approximately 3–5 days.

EXEMPLAR

FirstLanding’s atomic bundle allocator

Reuse its strongest properties: one locked allocation transaction, complete bundles, real bind checks, and generated environment overrides.

Intentional deviation: Aster leases ports only while the supervisor lives; it does not persist allocations for the lifetime of a Git worktree.

Recommendation: Option 1. The current named-port graph already expresses FirstLanding’s cross-service wiring; dynamic resolution and typed injection fill the two missing capabilities without creating a parallel port system.

2. Proposed DSL

# Existing forms remain static and backward compatible.
[dev.ports.postgres]
env = "POSTGRES_PORT"
default = 5432

# A dynamic root selects a free value from an inclusive range.
[dev.ports.platform]
allocation = "dynamic"
range = [4000, 4999]
preferred = 4000

# Existing offsets form an atomic bundle with their dynamic root.
[dev.ports.developer-portal]
default = 3300
offset_from = "platform"
offset_base = 4000

[dev.ports.grpc-auth]
allocation = "dynamic"
range = [51000, 51999]
preferred = 51001

[dev.ports.grpc-admin]
default = 52001
offset_from = "grpc-auth"
offset_base = 51001

[dev.services.platform]
target = "//services/platform:dev"
port = "platform"
port_env = {
  PHX_PORT = "platform",
  GRPC_AUTH_PORT = "grpc-auth",
  GRPC_ADMIN_PORT = "grpc-admin"
}

[dev.services.developer-portal]
target = "//services/developer-portal:dev"
port = "developer-portal"
port_env = {
  PORT = "developer-portal",
  GRPC_AUTH_PORT = "grpc-auth"
}
env = {
  PLATFORM_API_URL = "http://localhost:{ports.platform}"
}

Static mode

An integer or existing detailed definition is static. allocation = "static" may be accepted explicitly but is never required.

Dynamic mode

range is required; preferred is optional and tried first. Dynamic definitions reject env, file_env, and offset_from.

Derived ports

A static offset may depend on a dynamic root. The allocator evaluates and claims the entire transitive bundle before committing any port.

Environment values

port_env maps a variable directly to a named port. Existing {port} and {ports.name} templates remain for composite values.

3. Cross-service semantics

  1. Named ports are the contract. Producers and consumers reference the same name; Aster does not infer ownership from target dependencies.
  2. port_env is typed. Its value must be an existing named port and is injected as a decimal string after allocation. It overrides values loaded from the service’s env_files.
  3. env still wins over env_files. It expands {port} and {ports.name} after allocation. A duplicate key in both port_env and env is a configuration error.
  4. Selection remains explicit. Referencing another service’s port does not silently start that service. Groups must continue listing the services they run.
  5. Only owned listeners are claimed. Claim selected services’ primary ports, their port_env declarations, and the selected control port. Templates and TLS upstream routes consume resolved values without claiming external listeners.

4. Allocation lifecycle

1 · SelectResolve group and collect its complete named-port dependency set.
2 · LockTake the host-level allocator mutex shared by every local Aster process.
3 · ClaimTry candidates deterministically; exclude locked, listening, and wildcard-bound ports.
4 · RunHold per-port lease file handles while building the plan and supervising children.
5 · ReleaseDrop leases after child teardown; the OS releases leases if the supervisor crashes.
  1. Location: a per-user runtime directory shared across repositories, not a worktree directory. Ports occupy a host-global namespace, so a repo-local lock is insufficient.
  2. Atomicity: claim static ports, dynamic roots, and derived ports as one sorted bundle while holding the allocator mutex. On any failure, release the partial bundle.
  3. Crash safety: one lock file per port is held for the supervisor lifetime. A stale metadata record is advisory; an unlocked lease is reclaimable. If a force-killed supervisor leaves an orphan listener, availability probes continue excluding its port.
  4. Availability: lock ownership prevents Aster-versus-Aster races. A loopback connect plus wildcard bind probe rejects listeners and bound sockets owned by other programs. Arbitrary services cannot eliminate the final external bind race without socket activation.
  5. Restarts: service restarts retain the same lease. The allocation ends only when the owning services up supervisor finishes.

6. Acceptance gates

Existing static configurations resolve exactly as before.
Two simultaneous Aster runs cannot claim the same port.
Dynamic roots and every derived port commit atomically.
Normal exit and crash both make allocations reclaimable.
Service env files cannot overwrite allocated port_env values.
Consumers receive dependent named ports and composed URLs correctly.
Concurrent service groups reserve only their required port closure.
A live FirstLanding stack and a concurrent allocation plan receive disjoint bundles.

Non-goal: socket activation for arbitrary child processes. Aster guarantees conflict freedom among cooperating Aster supervisors and rejects already-bound external ports; it cannot transfer pre-bound sockets to frameworks that do not support it.
