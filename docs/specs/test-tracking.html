Aster Test Tracking

Aster records every test it runs in CI, one record per test per attempt. It uploads those records to aster-srv, a service in this repo deployed on our GKE cluster. The service finds flaky tests, and Aster uses its quarantine list to stop known flakes from failing the build.

Decisions
CI firstBuilt for GitHub Actions runs. Local history is not in scope.
Service lives in asterA Cargo workspace member at crates/aster-srv. Its image is published to GHCR, and it is deployed from firstlanding's Pulumi.
Quarantine passes the buildA target whose only failures are quarantined tests reports passed, with a warning. Quarantined tests still run and still upload.
30-day retentionRun, target and test rows, plus the raw NDJSON in GCS, are dropped after 30 days. Only each test's current state is kept beyond that.
Why
  • firstlanding RCA (2026-09-27..30): 271 failed CI jobs, 38% flaky. They cluster in Intern Browser, Services Platform (DBConnection.OwnershipError) and Other Elixir canonical-e2e.
  • scripts/ci/retry_failed_targets.py retries whole targets, so one flaky ExUnit test reruns all of mix test and the DB reset. It keeps no memory between runs.
  • CI failure reports scrape failing tests out of job logs. Aster already knows each runner's argv and can capture the results directly.
  • Aster has a content hash of every target's inputs. If two runs have the same hash and different outcomes, the test is proven flaky. Generic tools have to guess this from commit history.
Architecture
Capture by runner

Strategies in order of preference: read report files the tool already writes, add a reporter flag, parse stdout. Aster adds a flag only when its argv parser in src/plugins/related_tests.rs or rust_related.rs understands the command. Report files go under $RUNNER_TEMP (or the system temp dir), never inside the checkout.

Wire format

One NDJSON file per Aster invocation, gzipped on upload. test_id = sha256(project | file | suite | name). failure_hash is the failure message with numbers, hex addresses, PIDs and temp paths stripped, then hashed, so similar failures group together.

{"type":"run","run_id":"gh:ArchAstro/firstlanding:18233412:1:test-ci:services-platform","repo":"ArchAstro/firstlanding",
 "sha":"9f1c…","branch":"main","pr":null,"workflow":"CI","job":"test-ci","attempt":1,"lane":"services-platform",
 "runner":"blacksmith-8vcpu-ubuntu-2404","aster_version":"0.18.0","started_at":"2026-10-13T17:02:11Z"}
{"type":"target","address":"//services/platform:test-ci","input_hash":"sha256:4be2…","status":"failed",
 "cached":false,"duration_ms":412233,"capture":"exunit-formatter","confidence":"complete","exit_code":2}
{"type":"test","target":"//services/platform:test-ci","test_id":"c81e…","file":"test/platform/agents_test.exs",
 "suite":"Platform.AgentsTest","name":"test creates an agent","outcome":"fail","attempt":1,"duration_ms":1840,
 "failure_hash":"f3a9…","message":"** (DBConnection.OwnershipError) cannot find owner for …"}
  • Passing tests carry only test_id, outcome and duration_ms.
  • message is cut to 4 KB, with secrets scrubbed (tokens, Bearer …, URLs containing credentials).
  • A cached target emits a target record with cached:true and no tests.
  • input_hash is computed even with --no-cache, because the classifier needs it.
Flake classification

Definite flake

  • Same input_hash, both pass and fail, within 30 days.
  • Or it fails, then passes on retry, in the same run.

Likely flake

  • Fails on main but passes on the next run, with no change to its target.
  • Fails on a PR whose diff --related says cannot reach it.

Broken

  • Fails on every run since commit X with the same failure_hash.
  • Never quarantined. It is reported with X as the likely cause.

flake_score = definite events × 3 + likely events, over a rolling 7 days.

Quarantine
A failed target reports passed (quarantined: N) only if all of these hold:
  1. Capture confidence is complete.
  2. After retries, every failing test is in the quarantine list (server entries plus the repo file).
  3. The exit code is the runner's "tests failed" code, not a crash, compile error, timeout or signal. The number of failures parsed matches the runner's own summary.
  4. ASTER_QUARANTINE is not off.

Entering quarantine

  • Automatically: 2 or more definite-flake events in 7 days, from 2 or more different runs.
  • Manually: an entry in aster-quarantine.toml in the repo (reviewed in a PR, so it is auditable). v1 needs no human auth on the service.

Leaving quarantine

  • Released automatically after 20 consecutive passes while quarantined.
  • Expires after 30 days at most (matches retention), then is re-evaluated from scratch.
  • Manual entries need a reason and expires date.

Visibility

  • Quarantined tests still run and upload.
  • Each suppressed failure gets a GitHub warning annotation and a step-summary row.
  • The quarantine snapshot (version and count) is printed at start.

Service outage

  • Use the cached .aster/quarantine.json if it is less than 24 hours old.
  • Otherwise only the repo file applies. Nothing extra gets suppressed.
  • A failed upload never fails the build.

Risks
  • A reporter flag changes how a user's command behaves. Mitigation: add flags only through the argv parser, and add nothing when the parse is unsure. Each runner gets a golden test that the console output is unchanged.
  • The ExUnit .beam doesn't load on a project's OTP version. Mitigation: compile it on the oldest supported OTP, check at load time, and fall back to the stdout parser.
  • Quarantine hides a real regression. Mitigation: "broken" tests are never quarantined, entries expire, there are annotations on every suppression, and a kill switch.
  • Postgres volume. Example: 40k tests × 300 jobs a day ≈ 12M rows a day, about 360M at 30 days. Mitigation: daily partitions, passing-test rows kept small, ClickHouse only if queries get slow.
Open questions
  1. Auto-quarantine threshold (built as the proposal, and configurable: ASTER_SRV_QUARANTINE_RUNS, default 2; 1 means a single proven flake): should a test enter quarantine after 2 proven flakes from 2 different runs in 7 days, or after a single one? A proven flake means the test passed and failed on identical inputs (the same input_hash). One event is proof enough on its own, but an outage across CI (database down, network blip) would then quarantine every test it touched in a single run.
